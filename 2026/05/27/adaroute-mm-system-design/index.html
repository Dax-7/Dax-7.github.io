AdaRoute-MM 系统设计：面向边缘设备的本地多模型路由推理

背景

在边缘设备上部署大模型推理时，最直接的问题不是“模型能不能跑”，而是“能不能在有限资源下稳定、快速、合理地跑”。

以 Jetson Xavier NX 这类设备为例，本地内存、显存、算力和散热能力都比较有限。如果始终使用大模型，推理质量可能更好，但时延和资源占用较高；如果始终使用小模型，速度更快，但复杂任务上的回答质量容易下降。

AdaRoute-MM 的目标是构建一个面向边缘设备的本地多模型路由推理系统。系统不依赖云端 API，而是通过本地 Ollama 调用多个不同规模的模型，并根据输入任务难度和设备资源状态动态选择合适的模型。

简单来说，AdaRoute-MM 想解决的问题是：

在资源受限的本地设备上，如何让小模型、中模型和大模型协同工作，而不是固定使用某一个模型。

系统目标

AdaRoute-MM 的设计目标包括：

  • 所有模型本地推理，不依赖云端服务；
  • 支持纯文本输入，也支持可选图像输入；
  • 使用 Router 判断任务难度；
  • 根据任务难度和资源状态选择不同规模模型；
  • 小模型输出不可靠时触发 fallback；
  • 记录完整日志，方便后续分析准确率、时延和模型调用分布；
  • 模块之间保持解耦，便于替换模型和调整路由策略。

系统的重点不是单个模型的性能，而是本地推理流水线的整体调度能力。

Fallback 机制

Router 并不总是完全准确，小模型也可能在某些任务上输出不可靠答案。因此系统引入 fallback 机制。

常见的 fallback 触发条件包括：

  • 模型输出为空；
  • 输出明显过短；
  • 输出格式错误；
  • 数值题没有给出数值；
  • 选择题没有给出明确选项；
  • 模型回答“不知道”或“无法判断”；
  • 推理调用超时或失败。

例如，一个数值题需要输出具体答案，但小模型只回答了计算方法，没有给出最终数值，此时系统可以触发 fallback，交给 Medium 或 Large 模型重新回答。

Fallback 不应无限升级。实际系统中通常会限制最大 fallback 次数，避免单次请求时延失控。

工程实现中的注意点

Router 也有成本

多模型路由并不是免费的。Router 本身也需要一次模型调用，因此会增加额外时延。如果 Router 太慢，简单任务反而可能比直接调用小模型更慢。

因此，Router 应该尽量轻量，并且输出格式要稳定。

模型切换开销不能忽略

在本地环境中，频繁切换模型可能导致额外加载开销。对于内存有限的设备，可以考虑让 Router 和 Small 模型常驻，Medium 和 Large 按需调用。

路由策略要偏保守

边缘设备上，系统稳定性通常比单次最高准确率更重要。当资源紧张时，系统应该允许降级，而不是强行调用大模型。

Fallback 要有上限

Fallback 可以提高质量，但也会增加时延。实际实现中需要限制 fallback 次数，例如最多升级一次，或者最多执行 Small → Medium → Large 的两级链路。

后续优化方向

AdaRoute-MM 后续可以从以下几个方向继续优化：

  1. 使用更轻量的 Router，减少路由阶段时延；
  2. 引入基于 embedding 或 kNN 的路由方法；
  3. 针对 numeric、choice、vision_qa 等任务类型设计更细的规则；
  4. 对 VLM 生成的视觉上下文进行缓存；
  5. 优化模型常驻策略，减少模型切换开销；
  6. 改进 Quality Checker，提高 fallback 判断可靠性；
  7. 在更接近 Jetson Xavier NX 的环境中测试长时间运行稳定性。

总结

AdaRoute-MM 的核心思路是：在边缘设备上，不固定使用单一模型，而是根据任务难度和资源状态动态选择合适的本地模型。

对于简单任务，系统优先使用小模型降低时延；对于复杂任务，系统调用更强模型提高质量；当设备资源紧张时，系统可以自动降级；当输出不可靠时，系统可以通过 fallback 重新推理。

从工程角度看，AdaRoute-MM 更像是一个本地推理调度系统，而不是单纯的模型调用脚本。它关注的是多个本地模型如何在有限资源下协同工作，并在准确率、时延和稳定性之间取得可控的平衡。
